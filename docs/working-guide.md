# Working guide

> Use Slate for the project's planning and specifications. Keep the future product,
> its content model, and its UI independent of this documentation harness.

## Preview locally

From the repository root in PowerShell:

```powershell
git submodule update --init --recursive
node .\slate\scripts\runtime-host.mjs check --repo . --host docs
python -m http.server 8080 --bind 127.0.0.1 --directory .\docs
```

Open **http://127.0.0.1:8080/**. Stop with `Ctrl+C`.
Use an available port if `8080` is already in use. Keep the bind address on loopback.
Opening the reader as a local file will not work.

Git, Node.js 22+, and Python 3 are sufficient for these commands.
No dependency installation or documentation build is needed.

## File ownership

| Location, relative to the repository | Owner and editing rule |
| --- | --- |
| `docs/overview.md`, `docs/brief.md`, `docs/working-guide.md` | Project content; edit directly |
| `docs/docs-manifest.json` | Project navigation; register every authored page with a useful title and icon |
| `docs/slate.config.json` | Project reader configuration and branding |
| `docs/project.theme.css` | Project theme token overrides; currently unchanged from the starter |
| `docs/index.html` | Host-owned reader entry, initially generated by Slate |
| `docs/shell/`, `docs/.slate-runtime.json` | Generated runtime and digests; sync from Slate, never hand-edit |
| `slate/` | Editable upstream submodule for reusable documentation-harness changes |
| `agentic-craft/` | Editable upstream submodule for reusable product-reasoning changes |
| `agent-orchestration/` | Editable upstream submodule for reusable execution-control changes |
| `.github/skills/slate/SKILL.md` | Thin agent adapter; points to the canonical authoring contract |
| Other `.github/skills/` folders and `.github/agents/` | Craft's and Orchestration's installed copies; edit canonical sources, then rerun the installers |
| `AGENTS.md` | Project-specific instructions and each harness's project facts, preserved by the installers |

Slate governs how these documents are rendered. Craft governs what the future
product should be and what success means. Orchestration governs how work on it is
carried out, checked, and handed over. None of them is product code, and Craft's
product component architecture does not replace Slate's reader.

## Add documentation when the brief arrives

1. Read the [initial brief](brief.md) and the provided source material first.
2. Follow `slate/SKILL.md` and its component catalog locally, or open the
   [pinned canonical Slate skill](https://github.com/prabinpebam/slate/blob/d594742a1a6582c5cb890fcb18e63bc798ced99e/SKILL.md).
   The docs-only preview intentionally does not serve repository files outside `docs/`.
3. Add focused Markdown pages or supported HTML body fragments in `docs/`.
   Use Slate's visual-first components when the source supports a useful visual.
   Do not add page-specific scripts or styles.
4. Register each page in `docs/docs-manifest.json`. Paths are relative to `docs/`;
   choose a content-appropriate Material Symbols icon. Add groups only as needed.
5. Link supporting material and record its source and status. Keep private or
   work-sensitive material out of published content; do not import collections
   without an explicit scope.
6. Check the affected navigation and links, then preview the changed pages.

Start small: the initial pages are entry points, not a predetermined documentation
taxonomy. Add plans, research, designs, specifications, or decisions when there is
actual material to document. Avoid empty placeholder specifications and fabricated
history, source excerpts, inventories, or measurements.

Keep one canonical statement of each requirement. Mark proposals and assumptions as
such; record accepted decisions only when the owner has actually made them.

## Check the host

```powershell
node .\slate\scripts\runtime-host.mjs check --repo . --host docs
```

This checks generated runtime identity and file hashes; it does not validate product
requirements or all authored content.

For content changes, also check manifest path uniqueness, page existence, relative
links, and rendering in the HTTP reader. Exercise search and navigation when their
inputs change. Run feature-specific Slate validators when using those features.

## Edit and push harness changes

All three harnesses are the owner's repositories, checked out as editable Git submodules:

| Local folder | Push destination | Configured update branch |
| --- | --- | --- |
| `slate/` | [prabinpebam/slate](https://github.com/prabinpebam/slate) | `main` |
| `agentic-craft/` | [prabinpebam/agentic-craft](https://github.com/prabinpebam/agentic-craft) | `main` |
| `agent-orchestration/` | [prabinpebam/agent-orchestration](https://github.com/prabinpebam/agent-orchestration) | `main` |

Each has its own working tree, branches, commits, and `origin`. Make a generic
improvement in the relevant source, not in a generated or installed copy. Follow
that harness's own `AGENTS.md`; keep product-specific decisions in this parent
repository. Put a change in the harness whose role it serves: product intent and
success criteria in Craft, execution practice in Orchestration, documentation
authoring and reading in Slate.

From the repository root, create a contribution branch in the harness you want
to change (choose an unused, descriptive branch name):

```powershell
# Choose the relevant repository; these are separate branches.
git -C .\slate switch -c improve-slate
git -C .\agentic-craft switch -c improve-craft
git -C .\agent-orchestration switch -c improve-orchestration
```

Edit and test the canonical source, then stage and commit only your intended
changes using that harness's Git repository. A commit in the parent repository
does not commit work inside a submodule. After reviewing the harness commit, push
the relevant branch:

```powershell
# Run only for the harness you changed and committed.
git -C .\slate push -u origin HEAD
git -C .\agentic-craft push -u origin HEAD
git -C .\agent-orchestration push -u origin HEAD
```

These commands publish contribution branches; they do not merge them into `main`.
Follow the repository's review and branch-protection rules. Pushes are manual
actions, not something the installed orchestration guidance authorizes on its own.

### Initialize and update the submodules

```powershell
# A fresh clone with all three harnesses at their pinned commits.
git clone --recurse-submodules https://github.com/prabinpebam/loushing.git

# An existing clone: check out the pinned commits, then confirm them.
git submodule update --init --recursive
git submodule status
```

`git submodule status` lists `slate`, `agentic-craft`, and `agent-orchestration`
with the pinned commit of each; a leading `-` means not initialized and a leading
`+` means the checked-out commit differs from the pin.

### Fresh clones and pinned revisions

`git submodule update --init --recursive` checks out the exact parent pins and
normally leaves submodules in detached HEAD state. That is expected. The branch
creation commands above work from a detached HEAD and preserve the pinned starting
point. Do not commit harness work on an unnamed detached HEAD.

The `branch = main` settings in `.gitmodules` name the branch for explicit remote
updates; they do not turn a pinned checkout into a floating dependency.

To adopt upstream `main` deliberately, first commit or otherwise preserve local
work, then run these commands for the relevant harness:

```powershell
git -C .\slate switch main
git -C .\slate pull --ff-only

git -C .\agentic-craft switch main
git -C .\agentic-craft pull --ff-only

git -C .\agent-orchestration switch main
git -C .\agent-orchestration pull --ff-only
```

Alternatively, `git submodule update --remote <folder>` fetches and checks out the
configured branch's latest commit as a detached HEAD. Review the new revision and
refresh the affected host surfaces below. Avoid running submodule updates over
uncommitted harness work.

## Refresh the host from canonical sources

### Slate runtime

After a Slate runtime change or intentional revision update:

```powershell
node .\slate\scripts\runtime-host.mjs sync --repo . --host docs
node .\slate\scripts\runtime-host.mjs check --repo . --host docs
```

The sync preserves host-owned content, configuration, theme, and reader entry.
When updating, compare relevant upstream reader-entry changes explicitly and validate
the real host before committing the new pin and generated files.

### Craft skills and reviewers

After editing the canonical Craft source or updating its revision:

```powershell
node .\agentic-craft\tools\install.mjs . --for copilot --dry-run
node .\agentic-craft\tools\install.mjs . --for copilot
node --test .\agentic-craft\test\harness.test.mjs
```

The installer copies eight product-reasoning skills and two reviewers
(`grounding-critic`, `design-system-auditor`) into the workspace's `.github/`
folders; it does not change global agent settings. It leaves the Slate adapter and
other harnesses' files in place and preserves filled-in project facts in
`AGENTS.md`. The copied files are replaceable outputs, not the upstream source. Do
not customize them locally: rerunning installation overwrites same-named source files.

### Orchestration skills and reviewer

After editing the canonical Orchestration source or updating its revision:

```powershell
node .\agent-orchestration\tools\install.mjs . --for copilot --dry-run
node .\agent-orchestration\tools\install.mjs . --for copilot
node --test .\agent-orchestration\test\harness.test.mjs
```

The installer copies five execution skills (`orchestrate`, `execution-modes`,
`stage-validation`, `progress-review`, `coordinate`) and the `throughput-reviewer`
agent, and keeps its own section of `AGENTS.md` with the project facts it reads.
Add `claude` or `agents` (the `.agents/skills` folder Codex reads) to `--for` when
those agents are used here.

### Review installed copies when updating

Review the generated-file diff when updating: neither installer prunes files for
skills or reviewers removed upstream. Remove only confirmed obsolete harness-owned
files, never the Slate adapter or unrelated skills. For example, Craft 0.2.0 moved
its `orchestrate` skill and `throughput-reviewer` agent to Orchestration, so those
names now come from the Orchestration installer.

Tools and templates remain in each harness folder. Invoke tools from there; copy
or adapt templates into actual project documents only when needed. There are no
product specs, work plans, application tests, performance budgets, or design tokens
to invent during setup.

### Record the parent pins last

There are two levels of commits:

1. Commit, validate, and push reusable changes in the harness repository.
2. Refresh and verify this workspace, then commit the updated harness Git link and
   affected installed/generated files in the parent repository when requested.

The exact harness commit referenced by the parent must be reachable on the
harness remote before sharing the parent commit. Otherwise a collaborator cannot
initialize that submodule. If adopting a merged revision instead of the
contribution branch, switch to that revision and repeat the refresh and checks.

When only host content or project facts change, commit in the parent repository;
there is no reason to change any harness's pin.

Do not copy the full Slate package under an agent discovery directory or use its
runtime as the skills-browser application.
